## 2. 项目定位
### 2.1 产品目标
开发一款面向 macOS 的极简美股分析桌面端，核心能力是：
- 本地查看四大指数、个股和自定义板块的 K 线
- 使用 Longbridge OpenAPI 获取数据并本地化
- 支持自定义板块的等权/市值加权合成
- 支持盘中低频更新当天最新日 K
- 保证真实行情量上来时依然保持流畅、不假死、不丢输入焦点

### 2.2 首版平台
- 平台：`macOS`
- 打包形态：`.app + .dmg`
- 不纳入本期：`Windows`、`Linux`

### 2.3 首版范围
保留旧版全部主能力，并新增“盘中低频更新最新日 K”：
- 顶部四大指数切换
- 自定义板块列表
- 板块成分股列表
- 指数 / 板块 / 个股切图
- 日 K / 周 K 切换
- 板块等权 / 市值加权切换
- Longbridge 鉴权配置
- 本地 SQLite 持久化
- 板块异步构建
- 目标观点笔记
- 同步状态展示
- 盘中更新当天最后一根日 K

### 2.4 明确不做
- 分钟 K
- 逐笔成交
- L2 行情
- 复杂实时盘口
- 云端服务化
- 多端同步
- 多账户体系
- 策略回测

## 3. 旧版本已知问题与新版本必须规避的坑
以下问题已经在旧项目中真实出现，新版本必须从架构层避免：

### 3.1 前端渲染类问题
- 状态变化触发整页或整块 DOM 重建
- 设置页输入过程中因重渲染丢焦点
- 笔记输入和板块编辑时输入中断
- 图表挂载节点被替换，导致图表实例重建
- 盘中更新或同步轮询误伤设置窗口和输入表单

### 3.2 图表类问题
- 目标切换时销毁并重建整张图表实例
- 范围切换、粒度切换、盘中更新都走全量重绘
- 图表数据和 UI 状态耦合过深，导致切图时主界面卡顿

### 3.3 后端同步类问题
- `save_board()` 同步串行执行：拉数据、写库、重算板块、返回 UI
- 新建板块成员一多时，前端长时间等待请求返回
- 每只股票单独请求、单独写库、单独提交事务
- 批量构建时缺乏并发控制
- 板块构建状态只存在内存，不可查询、不可恢复

### 3.4 缓存与计算类问题
- 重复请求相同 symbol
- 重复计算周 K、板块 K 线和图表 payload
- 一次局部变更触发全量缓存失效
- 板块构建完成后全量 `cache.clear()`

### 3.5 宿主与通信类问题
- `pywebview + localhost + 自定义 bridge` 维护成本高
- 多窗口状态同步脆弱
- 前端轮询过重，导致状态流和视图流耦合

### 3.6 新版本后端侧对应解决方式
为彻底规避上述旧问题，新版本后端必须固定采用以下方案：
- `save_board()` 拆成快路径与后台路径；命中后台路径时只做本地校验、落库、写状态和入队，不在返回前发起远端请求
- `startup / manual` 同步按本地 `latest_trade_date` 做增量补缺，避免每次都回退到全量历史
- `board_build` 固定按 `5` 个成分股一批、批内最多 `3` 并发、同一时刻仅 `1` 个构建运行，避免大板块把主流程拖死
- 缓存拆成原始日线、周线聚合、图表 payload、live overlay 等分层内存，并只做受影响目标的局部失效
- 盘中链路固定为单活动 watch，本地 `America/New_York` 规则日历快速判定开闭市，provider 冷启动通过后台 `prewarm` 分摊
- 盘中 overlay 只更新当天最后一根 bar；板块 watch 先去重成分股 quote，再按变化量决定是否推送 event，避免轮询风暴与整段历史重算

### 3.7 新版本前端侧对应解决方式
为彻底规避上述旧问题，新版本前端必须固定采用以下方案：
- 主窗口与设置窗口保持独立入口，`main.ts / settings.ts` 只负责调用 `mountMainWindow()` / `mountSettingsWindow()`；`src/app/` 只负责启动编排、listener 注册和启动诊断
- 状态固定拆成 `appStore / selectionStore / chartStore / syncStore / boardBuildStore / settingsStore / noteStore`，禁止再次回到“大对象一次 setState 触发整页重渲染”
- 主图固定为单实例控制器；切目标、切粒度、切范围和盘中 overlay 都只允许走 `setData()` / `updateOverlay()`，不替换 mount 节点
- 设置窗口固定走 `settings-only` 初始化；`settings-saved` 只驱动主窗口目录级补查，不得重放主窗口整套 `bootstrap`
- 板块构建、同步状态和盘中 live 只允许局部更新当前受影响区域，不得打断设置、笔记和板块输入
- 盘中事件固定按 `watchId + targetType + targetId + granularity + boardAlgorithm + updatedAt` 做归属和新旧判断，旧事件直接丢弃
- 当前图表控制器允许先以单实例占位实现落地，但接口 `mount()` / `setData()` / `updateOverlay()` 自 Step 1 起不得再变

## 4. 技术栈定稿
### 4.1 桌面与前端
- 桌面壳：`Tauri 2`
- 前端框架：`Svelte 5`
- 语言：`TypeScript`
- 构建工具：`Vite`
- 样式：`Svelte scoped CSS + 全局 design tokens`
- 图表：`Lightweight Charts 5.x`

### 4.2 后端与存储
- 核心服务：`Rust`
- 异步运行时：`tokio`
- 数据库：`SQLite`
- SQLite 驱动：`rusqlite`
- 凭证存储：`macOS Keychain`

### 4.3 不采用的方案
- 不使用 `pywebview`
- 不使用 React
- 不使用 SvelteKit
- 不使用 `tauri-plugin-sql` 作为业务主数据访问层
- 不让前端直接读写 SQLite

### 4.4 选型理由
- `Tauri 2` 提供更稳的桌面宿主、窗口管理和事件通信
- `Svelte 5` 更适合做细粒度 UI 更新，天然避免旧版整页重建问题
- `Rust` 更适合承接同步任务、板块构建、缓存和本地数据服务
- `Lightweight Charts` 更适合单图、局部更新、实时最后一根 bar 覆盖

## 9. 板块构建与同步模型
### 9.1 `save_board()` 双路径
必须保留两条路径：

1. **快路径**
- 本地数据已齐
- 直接重算并立即可用

2. **后台路径**
- 缺历史数据
- 立即返回
- 后台启动 `board_build`

### 9.2 快路径保护阈值
即使本地数据已齐，也不是所有板块都允许走快路径。

必须转后台 `board_build` 的条件：
- `成员数 > 20`
- 或 `预估重算 bars > 10_000`

满足任一条件即强制后台处理。

### 9.3 `board_build` 固定规则
- 每批 `5` 个成分股
- 批内最多 `3` 并发
- 同一时刻只允许 `1` 个板块构建处于 `running`
- 首建默认只拉最近 `1Y/day`
- 完整历史回补交给 `startup/manual`

### 9.4 板块重算要求
- 只重算当前板块
- 禁止因为共用 symbol 连带重算其他板块
- 完成后只失效当前板块和本批影响到的 symbol 缓存
- 禁止 `cache.clear()` 全量失效

### 9.5 前端配合要求
- 后台构建状态通知优先走 `Tauri event`
- 前端事件断连或应用冷启动恢复时，再调用 `get_board_build_status()` 补状态
- 不以高频轮询作为主通路

## 10. 盘中最新日 K 方案
### 10.1 首版口径
首版盘中更新只做：
- 免费
- 低频
- 只更新当天最后一根日 K

不做：
- 分钟 K
- 逐笔
- 盘口
- 高频实时订阅

### 10.2 更新策略
- 只监听当前活动目标
- 默认 `15s` 更新一次
- 仅在美股盘中运行
- 应用切后台、窗口隐藏或切目标时停止旧 watch

### 10.3 个股/指数
使用 quote 快照更新当天 bar：
- `open`：开盘后固定
- `high`：盘中向上扩展
- `low`：盘中向下扩展
- `close`：始终等于最新价
- `volume`：跟随最新累计成交量

### 10.4 板块
只重算“今天这一根板块 bar”：
- `equal_weight_v1`：按成员股当日收益等权更新
- `market_cap_weight_v1`：使用股份数 × 价格估算动态权重

补充口径冻结：
- 历史板块 K 线与成员权重展示，统一使用“本地最新可用收盘价 × 本地最新股份数据”
- 盘中 overlay 允许使用“当前 quote.close × 本地最新股份数据”
- 不允许把 `market_cap_weight_v1` 实现成“只按 shares 占比”

如果市值权重所需股份数据不完整：
- 降级为最近可用权重快照
- 在 `meta` 中明确返回权重口径说明

### 10.5 落库规则
盘中更新不高频写 SQLite：
- 盘中最新 bar 作为内存 overlay
- 正式落库仍由后端同步任务完成

### 10.6 失败回退
如果盘中 quote 不可用、限频或异常：
- 自动退回到最近一次落库的日 K
- 不阻塞 UI
- 不抛致命错误

## 11. 缓存与性能要求
### 11.1 缓存层次
必须实现三层缓存：
- 原始日线序列缓存
- 周线聚合结果缓存
- 最终图表 payload 缓存

### 11.2 性能约束
新版本必须从实现上规避旧版这些问题：
- 重复请求相同 symbol
- 重复生成相同周 K
- 重复计算整段板块历史
- 一次局部变化触发全局缓存失效

### 11.3 明确禁止
- 全量 `cache.clear()`
- 图表更新时重新 mount
- 板块构建每处理一个 symbol 就推一次 UI
- 后台任务进度只存在内存
- 同步或盘中更新打断输入焦点

## 14. 测试要求
### 14.1 功能测试
- 指数、板块、个股切图与旧版行为一致
- 等权/市值切换正确
- 日 K / 周 K 切换正确
- 笔记保存和恢复正确
- 设置窗口独立打开和保存正确

### 14.2 性能测试
- 冷启动到可交互：`< 2.5s`
- 缓存命中切图：`< 100ms`
- `save_board()` 后台路径返回：`< 300ms`
- 创建 `50` 个成分股板块时 UI 仍可操作
- 盘中更新持续 `30` 分钟后无明显内存上涨和无整页卡顿

### 14.3 回归测试
- 输入持续进行时不丢焦点
- 设置窗口输入不被后台同步和盘中更新打断
- 图表实例不被销毁重建
- 板块构建中切目标不报错
- 后台任务完成后只更新相关区域

### 14.4 异常测试
- Longbridge 凭证错误
- 远端限频
- 单个成分股拉数失败
- 板块部分成功
- 应用休眠恢复
- 网络中断恢复

### 14.5 打包验收
- `.app / .dmg`
- 签名
- notarization
- Gatekeeper 首开
- Keychain 正常读写

### 14.6 后端验收分层
后端验收必须明确区分自动化回归与真实凭证烟测：
- 自动化回归默认基于 fake provider / stub / 半真数据夹具，必须可稳定由 `cargo test` 执行
- 真实 Longbridge 凭证、真实网络状态、真实盘中时段下的烟测与性能样本单独留证，不并入默认自动化测试
- `start_chart_watch()` / `stop_chart_watch()` 的 SLA 只统计 command 自身；provider 预热耗时与首轮 quote 耗时必须单独记录
- `30` 分钟持续 watch 稳定性至少保留 `0 / 10 / 20 / 30` 分钟的内存或 RSS 采样，以及 event 数量和 SQLite / `WAL` 增长摘要

## 16. 结论
`new_stock` 的实现原则是：

`保留旧产品行为与视觉，彻底更换性能架构`

成功标准不是“新技术栈跑起来”，而是：
- 真实 Longbridge 数据量上来后依然流畅
- 新建大板块不假死
- 图表切换稳定
- 输入不丢焦点
- 盘中更新只影响当前图表，不误伤其他界面
