## 3. 本轮交付目标
本轮优化完成后，后端必须达到以下状态：
- 大板块保存前预判阶段不再逐成员查库
- 板块重算不再逐成员读取完整历史

## 5. 统一实现规则

### 5.1 所有阶段都必须遵守
- 不允许在成员循环里反复进入 repository
- 不允许在长事务里发远端网络请求
- 不允许在 watch 循环里查整段历史
- 不允许保留 `contains()` 模糊失效
- 不允许保留“整表删 + 整表写回”作为默认板块重算路径

### 5.2 async 路径的额外规则
以下重操作不得直接压在 async 热路径里：
- 大批量 SQLite 读
- 大批量 SQLite 写
- 大板块聚合

需要这样处理：
- 在 `board_build::run()`、`SyncService::run()`、`chart_watch` 的已证实重型本地计算路径中，使用 `tauri::async_runtime::spawn_blocking`
- `spawn_blocking` 闭包内部重新使用 `Database` 打开连接，不要跨线程传 `Connection`
- 不允许把所有 DB 读写机械地一层层包进 `spawn_blocking`
- 只有满足以下条件时才允许引入 `spawn_blocking`：
  - 已有 telemetry 或 profile 证明该路径是明显慢点
  - 该路径是本地 CPU / I/O 重操作，而不是轻量状态查询
  - 引入后不会破坏现有 command 的快返回语义

### 7.4 这 4 个接口的实现要求
- 空输入必须直接返回空结果
- 每个接口只允许打开 `1` 个 SQLite 连接
- 每个接口只允许执行 `1` 条主查询 SQL
- `list_symbols_by_ids_batch()` 返回结果必须按输入 `target_ids` 顺序重排
- `list_daily_bars_batch()` 返回结果必须按 `target_id -> trade_date ASC` 排序
- `list_first_closes_by_ids()` 用于后续尾部重算，不允许读取完整历史后再在 Rust 里取第一条

### 7.5 必须使用的 SQL 形状

#### 批量 symbol 查询
```sql
SELECT target_id, target_type, display_code, name, market, security_type,
       currency, total_shares, circulating_shares, updated_at
FROM symbols
WHERE target_id IN (?, ?, ...)
```

#### 批量 bar 统计
```sql
SELECT target_id, COUNT(*) AS bar_count, MAX(trade_date) AS latest_trade_date
FROM daily_bars
WHERE target_id IN (?, ?, ...)
GROUP BY target_id
```

#### 批量日线读取
```sql
SELECT target_id, trade_date, open, high, low, close, volume, source, updated_at
FROM daily_bars
WHERE target_id IN (?, ?, ...)
  AND (?start_date IS NULL OR trade_date >= ?start_date)
ORDER BY target_id ASC, trade_date ASC
```

#### 批量首根收盘价读取
```sql
SELECT bars.target_id, bars.trade_date, bars.close
FROM daily_bars bars
INNER JOIN (
  SELECT target_id, MIN(trade_date) AS first_trade_date
  FROM daily_bars
  WHERE target_id IN (?, ?, ...)
  GROUP BY target_id
) firsts
  ON firsts.target_id = bars.target_id
 AND firsts.first_trade_date = bars.trade_date
ORDER BY bars.target_id ASC
```

- “删掉真实板块后 watch 还能继续推 overlay” 不得作为通过标准

## 10. Phase D：尾部增量重算

状态：未开始

当前未落地：

- `board_build::run()` 末尾仍是整段 `compose_board_bars() + save_board_chart()`

说明：
- 下面 10.1 - 10.9 是目标态增量重算方案，不代表当前代码已经支持 `tail append`

### 10.1 本阶段必须修改的文件

### 10.2 先修正当前板块聚合器的重算能力
当前 `build_board_bars()` 会把每个成分股第一根 bar 的 `close` 作为归一化基值。

这意味着：
- 若只读取后缀 bars，直接调用当前 `build_board_bars()` 会改变整条板块曲线的尺度
- 所以要做尾部重算，必须显式传入每个 symbol 的固定 base close

### 10.3 在 `aggregator.rs` 中新增以下能力
把 `WeightedSeries` 改成带 `target_id`：

```rust
pub struct WeightedSeries {
    pub target_id: String,
    pub weight: f64,
    pub bars: Vec<DailyBarRecord>,
}
```

新增：

```rust
pub fn build_board_bars_with_base(
    series: &[WeightedSeries],
    base_close_by_id: &HashMap<String, f64>,
) -> Vec<BarPoint>;
```

规则：
- `build_board_bars()` 保留，对旧调用兼容
- `build_board_bars()` 内部可以委托给 `build_board_bars_with_base()`
- `build_board_bars_with_base()` 的 base close 必须来自 `list_first_closes_by_ids()`

### 10.4 在 `sqlite.rs` 中新增以下接口
```rust
pub fn replace_board_chart_tail(
    &self,
    board_id: &str,
    algorithm: &str,
    recompute_from_date: &str,
    bars: &[BarPoint],
) -> AppResult<()>;
```

实现规则：
- 单事务
- 先删后缀，再写新后缀
- 不允许删整块历史

必须使用以下 SQL：

```sql
DELETE FROM board_daily_bars
WHERE board_id = ?1
  AND composition_algorithm = ?2
  AND trade_date >= ?3
```

### 10.5 `save_board_definition()` 必须先拆成“元数据更新”和“成分变更”
当前 `save_board_definition()` 不能再维持“每次保存都删整块 `board_daily_bars`”。

必须改成以下规则：
- 仅改名、改排序、改非成分字段：
  - 不删除当前 `board_daily_bars`
  - 不把首个 `get_chart(board)` 推回完整重算
- 成员集合变化或算法变化：
  - 允许把该板块标记为需要重算
  - 但后续必须继续按 `tail append / full rebuild` 规则处理

禁止：
- 任何 `save_board_definition()` 调用默认删除整块 `board_daily_bars`

### 10.6 `recompute_from_date` 规则
只允许以下两种模式：

#### `full rebuild`
仅在以下条件下允许：
- 板块成员变更
- 板块算法变更
- `CURRENT_BAR_ADJUSTMENT_POLICY` 变化，导致复权 / 调整口径版本变化
- 本地历史存在补洞
- 旧日期被历史修复重写
- 当前 `board_daily_bars` 为空

#### `tail append`
满足以下条件时必须使用：
- 板块成员未变
- 算法未变
- 仅尾部新增 bars
- 历史连续

### 10.7 `board_build::run()` 必须改成以下规则
- 新建板块首次构建：允许 `full rebuild`
- 已存在板块再次构建：
  - 先判断是否命中 `full rebuild` 条件
  - 否则走 `tail append`
- 只要命中 `CURRENT_BAR_ADJUSTMENT_POLICY` 变化，必须强制 `full rebuild`
- `tail append` 时：
  1. 计算 `recompute_from_date`
  2. 通过 `BoardDataBundle` 只读取 `>= recompute_from_date` 的 member bars
  3. 读取 `first_close_by_id`
  4. 调用 `build_board_bars_with_base()`
  5. 调用 `replace_board_chart_tail()`

### 10.8 `get_chart(board)` 的回退规则
- 如果 `board_daily_bars` 为空，允许按当前逻辑做一次完整构建
- 但只允许在“板块根本没有物化结果”时这样做
- 不允许因为普通增量同步后 materialization 被删掉就整块重算

### 10.9 本阶段完成标准
- `save_board_chart()` 不再是普通增量场景的默认写入入口
- `save_board_definition()` 不再因改名或排序而清空 `board_daily_bars`
- `board_build::run()` 已具备 `tail append`
- 存在测试证明：相同数据下，完整重算结果与后缀重算结果一致

当前未落地：

说明：
- 下面 11.1 - 11.8 是 Phase E 目标交付，尤其是并发和后缀重算接入，目前都还没做

### 11.1 本阶段必须修改的文件
- `src-tauri/src/services/sync.rs`
- `src-tauri/src/repositories/sqlite.rs`
- `src-tauri/src/services/runtime.rs`
- `src-tauri/tests/step3_sync_and_build.rs`
- `src-tauri/tests/step7_startup_sync.rs`

### 11.2 `run_sync()` 必须改成以下顺序
1. 批量读取所有 symbol 的 `BarStats`
2. 根据 `latest_trade_date` 计算哪些 target 需要补数
3. 把待拉取目标按 `10` 个一批切分
4. 每批最多 `3` 并发远端拉数
5. 全部远端返回后统一批量写库
6. 找到受影响 `board_id`
7. 先计算受影响 board 的总数与预计重算 bars
8. 若未超过前台阈值，则顺序执行后缀重算
9. 若超过前台阈值，则转后台队列或后台任务继续执行
10. 最后再做缓存精确失效

### 11.3 `run_sync()` 本阶段必须删除的旧逻辑
- 删除“更新 symbol bars 后直接 `delete_board_daily_bars_for_boards()`”这条默认路径

替换为：
- 对受影响板块执行 `tail append`
- 只有命中 `full rebuild` 条件时才允许删整块旧 materialization

### 11.4 `run_sync()` 的前台护栏
`run_sync()` 当前是 command 直接 `await` 到结束的路径，因此不允许把大量板块后缀重算无限制塞进前台同步返回时间里。

必须新增前台护栏：
- 先计算：
  - `affected_board_count`
  - `estimated_recompute_bars`
- 仅在以下条件同时满足时，允许在前台顺序执行板块后缀重算：
  - `affected_board_count <= 3`
  - `estimated_recompute_bars <= 20_000`

超过任一阈值时，必须改为：
- bars 写库与 symbol 级 sync 状态仍在本次 `run_sync()` 内完成
- 板块重算转后台队列 / 后台任务继续执行
- `sync-status` 必须给出“symbol 已同步、board 重算继续处理中”的进度语义

说明：
- 上述阈值为执行基线，可根据 telemetry 微调
- 但不能删除“前台护栏 + 后台转移”这条机制

### 11.5 并发规则
- symbol 拉数：批大小 `10`，批内并发 `3`
- 板块后缀重算：顺序执行，不并发

板块后缀重算顺序执行的原因：
- SQLite 只有一个写者
- 本阶段先保守收敛，避免锁冲突

### 11.6 `sync-status` 与耗时预算
必须补充以下进度与预算规则：
- 小规模受影响板块前台路径：
  - `run_sync()` 仍以单次返回完成
  - release 口径下总耗时目标应保持在可接受范围内
- 大规模受影响板块后台路径：
  - `run_sync()` 不等待所有 board 后缀重算结束
  - 必须有 `sync-status` 或等价 telemetry 能区分：
    - symbol 同步进行中
    - symbol 同步完成
    - board 重算排队中
    - board 重算进行中
    - board 重算完成 / 部分失败

### 11.7 错误处理规则
- 单个 symbol 拉取失败，不能中断整个 sync job
- 单个 board 后缀重算失败，必须记录日志并继续处理下一个 board
- 但最终 `sync_status` 必须保留失败摘要

### 11.8 本阶段完成标准
- `run_sync()` 中不存在逐 symbol 串行 `await fetch_daily_bars()`
- `run_sync()` 在 bars 写入后，不再默认删除整块 `board_daily_bars`
- `run_sync()` 已具备前台阈值护栏，不能无限制把 board 重算压在同步返回里
