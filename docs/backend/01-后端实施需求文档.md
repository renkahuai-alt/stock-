# `new_stock` 后端实施需求文档

## 1. 文档目标
本文档只面向后端工程师，定义 `new_stock` 新项目的 Rust 核心服务、SQLite 数据层、同步与板块构建、盘中更新和性能要求。

后端实施原则只有两条：
- 前端只拿标准化结果，所有业务计算都在 Rust 后端完成
- 重点解决旧项目在真实 Longbridge 数据量下的阻塞、重复计算和缓存失控问题

## 2. 后端范围
后端必须实现：
- Tauri 宿主与窗口管理
- Tauri commands 和 events
- Longbridge 接入层
- SQLite schema、迁移和 repository
- 同步任务系统
- `board_build` 后台流水线
- 板块合成引擎
- 周 K 聚合
- 盘中 quote watch 与当天 overlay 生成
- 缓存系统
- Keychain 凭证存储

后端不负责：
- 页面布局
- 控件样式
- UI 视觉调整
- 前端组件组织方式
- 图表 UI 表现细节

## 3. 技术栈
- 桌面宿主：`Tauri 2`
- 核心语言：`Rust`
- 异步运行时：`tokio`
- 数据库：`SQLite`
- 驱动：`rusqlite`
- 凭证存储：`macOS Keychain`

优先策略：
- Longbridge 优先使用官方 Rust SDK
- 如果 SDK 某能力不足，再由 Rust 服务层补 HTTP/WebSocket client
- 前端对此无感知

## 4. 目录结构
Rust 项目目录固定为：

```text
new_stock/src-tauri/src/
  app_shell/
  commands/
  services/
  jobs/
  repositories/
  live_quote/
  chart_engine/
  secret_store/
  models/
  errors/
  events/
```

职责固定：
- `app_shell/`：应用生命周期、窗口管理
- `commands/`：前端可调用的 command
- `services/`：业务编排
- `jobs/`：同步、板块构建、watch 任务
- `repositories/`：SQLite 读写
- `live_quote/`：盘中低频 quote 获取
- `chart_engine/`：周 K 聚合、板块 K 线、overlay 组装
- `secret_store/`：Keychain
- `events/`：事件发送与 payload 规范

- `daily_bars`
- `boards`
- `board_members`
- `board_daily_bars`
- `sync_jobs`
- `sync_state`

### 5.1 `boards` 构建状态字段
必须保留：

- `build_phase`
- `build_total`
- `build_completed`
- `build_failed`
- `build_job_id`
- `build_message`

- 开启 `WAL`
- 数据库只由 Rust 后端访问
- 批量写入必须包事务
- 禁止每只股票单独 commit
- 禁止让前端直连 SQLite

### 6.3 契约要求
- command 和 event 命名固定，不允许实施阶段自行改名

- 后端不得把 UI 逻辑耦合进 payload

### 6.4 板块构建契约冻结
为避免前后端在 Step 3 发生运行时漂移，后端必须冻结以下口径：

`buildStatus` 只允许：
- `queued`
- `running`
- `succeeded`
- `failed`

`buildPhase` 只允许：
- `queued`
- `fetching_symbols`
- `fetching_history`
- `recomputing_board`
- `persisting`
- `completed`
- `failed`

`BoardBuildStatusPayload` / `board-build-status` event / `get_board_build_status()` 至少必须同构包含：
- `boardId`
- `name`
- `buildStatus`
- `buildPhase`
- `buildTotal`
- `buildCompleted`
- `buildFailed`
- `buildJobId?`
- `buildMessage?`
- `updatedAt`

`BoardSummary` 至少必须包含：
- `boardId`
- `name`
- `compositionAlgorithm`
- `buildStatus`
- `buildPhase`
- `buildTotal`
- `buildCompleted`
- `buildFailed`
- `buildJobId?`
- `buildMessage?`
- `updatedAt`

`NoteRecord` / `activeTargetNote` 至少必须包含：
- `targetType`
- `targetId`
- `content`
- `updatedAt`

说明：
- 若当前 Rust `models` 未补齐这些字段，优先改 `models` 与 `commands`，不要让前端自行兼容缺字段 payload。

## 7. 同步与板块构建模型
### 7.1 `save_board()` 双路径
必须保留：

1. 快路径
- 本地数据已齐
- 直接重算并立即可用

2. 后台路径
- 缺历史数据
- 立即返回
- 启动 `board_build`

### 7.2 快路径保护阈值
即使本地数据已齐，也要做保护：
- `成员数 > 20` 强制转后台
- 或 `预估重算 bars > 10_000` 强制转后台

### 7.3 `board_build` 固定规则
- 每批 `5` 个成分股
- 批内最多 `3` 并发
- 同一时刻只允许 `1` 个板块构建处于 `running`
- 首建默认只拉最近 `1Y/day`
- 完整历史回补交给 `startup/manual`

### 7.4 板块重算要求
- 只重算当前板块
- 禁止因为共用 symbol 连带重算其他板块
- 只失效当前板块和本批影响到的 symbol 缓存
- 禁止全量 `cache.clear()`

### 7.5 状态持久化
板块构建状态必须落库，不能只存在内存：
- 冷启动后可恢复
- 前端可查询
- 任务失败后可定位

## 8. `get_chart()` 生成原则
后端负责生成前端所需的所有标准化图表数据。

### 8.1 输入固定
- `targetType`: `index | board | symbol`
- `targetId`
- `granularity`: `day | week`
- `range`: `1m | 3m | 6m | 1y | 3y | all`
- `boardAlgorithm?`: `equal_weight_v1 | market_cap_weight_v1`

### 8.2 输出固定
- `meta`
- `bars`
- `latestTradeDate`
- `sourceStatus`
- `activeOverlay?`

### 8.2A `get_board_member_summaries(payload)`
输入固定字段：
- `boardId`
- `compositionAlgorithm`: `equal_weight_v1 | market_cap_weight_v1`

输出固定字段：
- `boardId`
- `compositionAlgorithm`
- `members`
- `updatedAt`

规则：
- 用于同一 `boardId` 下按不同算法返回成员权重
- `bootstrap().membersByBoard` 仍只承担“板块默认算法快照”职责
- 不允许要求前端在算法切换时复用旧的 `membersByBoard[boardId]` 结果
- 不允许让前端自己按 bars 或 shares 重新计算成员权重

### 8.3 后端负责的计算
- 历史 bars 裁剪
- 周 K 聚合
- 板块等权 K 线
- 板块市值加权 K 线
- 当前日 overlay 合并

前端不得自己做这些计算。

## 9. 盘中最新日 K 方案
### 9.1 首版范围
只做：
- 免费
- 低频
- 当前活动目标
- 当天最后一根日 K

不做：
- 分钟 K
- 高频实时订阅
- 盘口
- 逐笔

### 9.2 watch 策略
- 只监听当前活动目标
- 默认 `15s` 一次
- 仅在美股盘中运行
- 切换目标、窗口进入后台或主动停止时立即取消旧 watch

当前实现补充：
- `start_chart_watch()` 先走本地 `America/New_York` 交易时段判断，避免为判断开闭市阻塞远端请求
- 真实 quote 拉取放在后台 watch loop 内执行，command 层不等待首轮 quote 完成
- `AppRuntime` 固定维护单活动 watch、live overlay 内存层和 provider 预热状态

### 9.3 个股/指数
用 quote 快照更新当天 bar：
- `open` 固定
- `high/low` 动态扩展
- `close` 取最新价
- `volume` 取最新累计量

### 9.4 板块
只重算今天这一根板块 bar：
- `equal_weight_v1`：按成员股当日收益等权更新
- `market_cap_weight_v1`：优先使用股份数 × 价格估算动态权重

如果股份数据不完整：
- 降级为最近可用权重快照
- 在 `meta` 中明确标注

补充口径冻结：
- 历史板块 K 线和 `get_board_member_summaries()` 返回的成员权重：
  - 统一使用“本地最新可用收盘价 × 本地最新股份数据”
- 盘中 overlay：
  - 允许使用“当前 quote.close × 本地最新股份数据”
- 不允许把 `market_cap_weight_v1` 降格实现成“只按 shares 占比”

### 9.5 落库策略
- 盘中 overlay 不高频写 SQLite
- 正式落库仍通过同步任务完成
- 盘中更新只作为内存覆盖层

当前实现补充：
- `get_chart(day)` 只读合并活动 overlay，不回写正式历史缓存
- `get_chart(week)` 不合并 `day` live overlay

## 10. 缓存与性能要求
### 10.1 缓存分层
必须实现：
- Longbridge provider 实例缓存
- provider 后台预热状态
- 原始日线序列缓存
- 周线聚合结果缓存
- 最终图表 payload 缓存
- 盘中 live overlay 内存层

### 10.2 必须规避的旧版性能坑
- 重复请求相同 symbol
- 重复计算周 K
- 重复计算整段板块历史
- 一次局部变化触发全量缓存失效
- `save_board()` 同步串行拉完整历史
- 每只股票单独写库
- 每批次都推整页 UI 更新

当前实现补充：
- `save_board()` 先按本地历史与保护阈值分流；后台路径只落库、写 `build_*` 状态并异步入队，真正的远端拉数放到 `board_build`
- `startup / manual` 以本地 `latest_trade_date` 和下一交易日为锚点，只请求缺失区间，不重复全量回补连续历史
- `board_build` 固定 `5` 个成分股一批、批内 `3` 并发，并通过运行时 gate 保证同一时刻最多 `1` 个正式构建
- `get_chart()` 采用 raw daily / weekly / chart payload / live overlay 分层缓存，失效时只清受影响 target / board
- `watch` 走本地纽约时段快判、provider cache 与后台 `prewarm`，并在 overlay 无变化时跳过重复 event

### 10.3 后端性能目标
- `save_board()` 后台路径返回 `< 300ms`
- `50` 成分股板块创建不阻塞 UI
- 缓存命中后 `get_chart()` 快速返回
- 盘中 watch 持续运行时无明显资源泄漏
- `start_chart_watch()` 返回 `< 100ms`
- `stop_chart_watch()` 返回 `< 100ms`

当前实现补充：
- provider 冷启动预热成本允许放到后台，不计入 `start / stop` 的 SLA
- 预热触发点固定为：应用 `setup`、`bootstrap()`、`save_credentials(payload)`、`start_chart_watch(payload)`
- `save_credentials(payload)` 写入 Keychain 后必须清空 provider cache，再启动后台预热

测量要求：
- 性能验收默认以 `release` 构建为准
- 必须区分冷路径与热路径，不允许混成一个数字
- `start / stop` 的 SLA 只考察 command 自身，不把 provider 冷启动或首轮 quote 拉取耗时算进去
- Step 5 中关于测量方法、样本数、验收证据的规定，为最终收口口径

稳定性取证要求：
- `30` 分钟持续 watch 至少记录 `0 / 10 / 20 / 30` 分钟的进程内存或 RSS 采样
- 同时记录 `chart-live-update` 推送数量与 SQLite / `WAL` 增长摘要
- 若宣称“无明显内存上涨 / 无事件风暴 / 无多余写入”，必须保留对应采样表或日志摘录

## 11. 凭证与安全
- 凭证存储固定走 `macOS Keychain`
- 前端只提交表单，不持有长期明文凭证
- 后端负责读取、写入、校验和轮换逻辑
- 日志不得打印真实凭证

当前实现补充：
- provider 不直接长期持有旧凭证实例；凭证更新后必须失效运行时 provider cache
- 背景预热只建立 SDK 上下文，不得输出凭证内容或把凭证落到 SQLite

## 12. 后端测试要求
### 12.1 功能测试
- `bootstrap`
- `save_credentials`
- `get_chart`
- `save_board`
- `get_board_build_status`
- `run_sync`
- `start_chart_watch / stop_chart_watch`

### 12.2 性能测试
- 大板块后台构建
- 批量写库
- 缓存命中路径
- 周 K 聚合路径
- 盘中 overlay 更新路径
- `start_chart_watch()` 快速返回路径
- provider 预热后的首条 live event 路径
- `save_board()` 后台路径返回前无远端请求
- `startup / manual` 增量补缺路径
- `tail append` 与 `full rebuild` 分流路径
- `30` 分钟持续 watch 稳定性

执行口径：
- 自动化性能 / 回归测试默认必须可由 `cargo test` 稳定执行
- 自动化测试不依赖真实 Longbridge 凭证、真实网络状态或真实盘中时段
- 真实 Longbridge 凭证下的 release 烟测、冷 / 热路径样本、首条 `chart-live-update` 样本单独留证，不并入默认自动化测试

### 12.3 异常测试
- Longbridge 凭证错误
- 限频
- 单个 symbol 拉数失败
- 板块部分成功
- 网络中断恢复
- 应用休眠恢复
- 应用冷启动后旧任务状态恢复
- provider cache 失效与重新预热

### 12.4 回归测试
- 后台任务完成后仅失效局部缓存
- 状态持久化可恢复
- 快路径与后台路径都符合契约
- 不出现全量 `cache.clear()`
- `start_chart_watch()` 不等待远端 `market_status()`
- provider 预热后首条 `chart-live-update` 不再走冷启动秒级延迟
- `save_board()` 后台路径返回前无远端请求
- `startup / manual` 只补缺失区间
- 板块默认走 `tail append`
- 仅成员变更 / 算法切换 / 补洞 / 历史修复触发 `full rebuild`
- job 级 symbol 去重生效
- `board-build-status` 与 `get_board_build_status()` 字段同构
- `chart-live-update` 持续携带 `watchId`、`updatedAt`
- 同一 `watchId` 下 `updatedAt` 严格递增
- `save_credentials(payload)` 后 provider cache 正常失效并重新预热

### 12.5 Release 预检
- 现有用户数据库迁移成功
- `WAL` 在打包运行目录仍然开启
- 打包后 Keychain 读写可用
- `.app / .dmg` 可产出
- 签名可通过
- notarization 可通过
- Gatekeeper 首开行为正常
